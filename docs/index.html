Read this first — v1.0 has no authentication. The edge HTTP API and the HQ read API have no auth, and RBAC is defined but never enforced. Run this on a trusted local network or behind a VPN with your own auth in front — never on the open internet. Full details in the security review.

Option A — Docker Compose (recommended)

One command brings up the store daemon (edge, SQLite), the HQ read API, and a provisioned PostgreSQL that nothing connects to yet in v1.0.

1. Clone the repo and set your environment:

git clone https://github.com/kielforeman-collab/decor-pos.git
cd decor-pos
cp .env.example .env
# Edit .env: replace STORE_ID / ORG_ID with fresh UUIDv7s
# and set POSTGRES_PASSWORD. Never commit a real .env.

2. Start it:

docker compose up --build -d

3. Check it answers:

curl -s http://localhost:8080/health   # edge
curl -s http://localhost:3000/health   # api
curl -s http://localhost:3000/api-docs/openapi.json | head -c 400

Stop with docker compose down (volumes kept) or docker compose down -v (deletes the SQLite database and Postgres data). The edge database is the edgedata volume (/data/edge.db in the container) — back it up by copying it out:

docker compose cp edge:/data/edge.db ./

Honest caveat: the Docker image and the compose stack were validated by review and YAML parse only — docker build and docker compose up were never run in the build VM (no Docker daemon there). The build commands inside the image are the same cargo build --release --locked that is tested, but run it once on a Docker host and watch the first boot.

Option B — Single binary (no Docker)

Needs Rust 1.99+ and a C toolchain. Build the two binaries, then run the edge daemon and the read API against the same SQLite file:

cargo build --release --locked -p df-server -p df-api
./target/release/df-server edge --db sqlite:edge.db \
  --store-id <uuid> --org-id <uuid> --listen 127.0.0.1:8080
./target/release/df-api --db sqlite:edge.db \
  --org-id <uuid> --store-id <uuid> --listen 127.0.0.1:3000

df-server edge creates and migrates the SQLite database on open. df-api runs no migrations — the database must already exist.

Option C — Dev mode (edge + web apps)

For trying the screens. Start the edge daemon (Option B, or cargo run -p df-server -- edge --db sqlite:edge.db --store-id <uuid> --listen 127.0.0.1:8080), then any frontend with npm install && npm run dev. Each app talks to the edge on :8080.

Importing legacy Decor Fusion data

The migrator imports customers, products, formulas (tracking records only), AR balances and inventory from CSV, with SHA-256 checksums per file and row and a manifest of imported / skipped / failed rows. Re-importing is a no-op for rows already imported.

df-server migrate import --db sqlite:edge.db --org-id <uuid> \
  --store-id <uuid> --dir ./legacy [--out manifest.json]

Sample fixtures ship in crates/df-migrator/fixtures/.

What v1.0 does — and does not do yet

Working

  • Offline counter POS with tills, holds, quotes, returns, layaways, Z-reports, and replay-safe sync
  • Formula tracking (lookup by name/code, customer colour history, reorders) — the POS never drives a tint machine
  • Contractor AR: charge accounts, credit checks, FIFO payments, finance charges, Typst PDF statements
  • Vendor EDI (X12 850/855/856/810/832) with 3-way match, CRM, delivery dispatch and proof-of-delivery
  • Mobile PWA, contractor portal with online bill pay, BOPIS storefront
  • BI dashboards, eco-fee remittance, labour forecasting, legacy migrator, chaos-tested sync

Not yet / stubbed

  • No authentication on the edge or HQ APIs; RBAC defined but never enforced; portal scope is just the customer ID
  • PostgreSQL HQ mode is not implemented and the Postgres round-trip was never tested live
  • No live Stripe Terminal, no live payment/accounting/vendor APIs — mock provider only
  • No native Excel export (scheduled reports are CSV + PDF); SFTP is a local-folder stand-in; AS2 has no network/crypto
  • Tauri Mobile wrapper is files only (unverified, no Android SDK in the build VM); Docker image and Helm chart unrun
  • Benjamin Moore COLORx tint-machine integration is deferred post-v1.0 by design

Kubernetes (skeleton)

A Helm chart lives in deploy/helm/decor-pos/ (edge + API deployments, shared PVC, optional PostgreSQL). It is a skeleton — values are placeholders, services are ClusterIP only, and no Ingress is defined, deliberately, because v1.0 has no authentication. See docs/self-hosting.md for the install commands and the shared-PVC caveats.
