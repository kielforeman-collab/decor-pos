Authentication, RBAC, and sync hardening are live. Every edge and HQ API route is gated by Argon2id-backed session tokens (dfp_…) and per-route RBAC, contractor portal sessions are strictly scoped to their linked customer, store-to-HQ sync uses revocable store-scoped service tokens (dfs_…) with an F8 dead-letter queue and HQ conflict triage, and HTTP hardening (F10) enforces exact-origin CORS allowlists, per-IP auth rate limiting (429 + Retry-After), 4 MiB body caps, and defensive security headers.
TLS / reverse proxy reminder (F9). df-server speaks plain HTTP. Before exposing HQ or remote sync outside a trusted store LAN or VPN, terminate HTTPS (and optionally client-cert mTLS on /api/v1/sync/ingest) at a reverse proxy such as Caddy, nginx, or Traefik. See docs/security-review-v1.0.md.

Option B — Store Edge + PostgreSQL HQ (multi-store production)

df-server runs both store-level SQLite edge daemons and the central PostgreSQL HQ server from a single binary (requires Rust 1.85+ / 2024 edition if building from source):

1. Migrate and start PostgreSQL HQ:

export DATABASE_URL="postgres://decor:change-me@127.0.0.1:5432/decorpos"
df-server migrate schema --db "$DATABASE_URL"
df-server hq --db "$DATABASE_URL" --org-id <org-uuid> \
  --listen 127.0.0.1:3000 --cors-origin https://hq.example.com

2. Mint a store-scoped dfs_ sync service token (from CLI or the Admin → Service tokens screen):

df-server tokens create --db "$DATABASE_URL" \
  --org-id <org-uuid> --store-id <store-uuid> \
  --label "Main Store Edge"

3. Start the store's offline-first SQLite edge daemon with background HQ sync:

export DF_HQ_TOKEN="dfs_..."
df-server edge --db sqlite:edge.db \
  --store-id <store-uuid> --org-id <org-uuid> \
  --hq-url https://hq.example.com --sync-interval-secs 30 \
  --listen 127.0.0.1:8080 --cors-origin http://localhost:1420

df-server edge creates and migrates SQLite automatically on first boot and seeds the configured store row. Check GET /health on either server ({"status":"ok","version":"1.2.3"}).

Option C — Docker Compose + one-command .env

1. Clone the repo and generate a fresh .env with random UUIDs and PostgreSQL password (refuses to overwrite an existing .env):

git clone https://github.com/kielforeman-collab/decor-pos.git
cd decor-pos
./setup.sh        # Linux / macOS
# or: .\setup.ps1 # Windows PowerShell

2. Start the stack:

docker compose up --build -d
curl -s http://localhost:8080/health   # edge
curl -s http://localhost:3000/health   # api

Back up the edge SQLite database from the edgedata volume with docker compose cp edge:/data/edge.db ./. Note: docker-compose.yml still boots the standalone df-api service container rather than df-server hq and has not been live-tested in CI (no Docker daemon in the build VM).

Importing products & legacy Decor Fusion data

GUI spreadsheet import: in pos-desktop under Products → Import products (Manager/Admin), pick any .xlsx or .csv price list. SheetJS parses it in the browser, previews ready vs. skipped rows, and upserts SKUs safely.

Legacy CSV migrator: imports customers, products, formula tracking records, AR balances, and inventory with SHA-256 checksums and idempotent UUIDv5 re-imports (sample fixtures in crates/df-migrator/fixtures/):

df-server migrate import --db sqlite:edge.db --org-id <uuid> \
  --store-id <uuid> --dir ./legacy [--out manifest.json]

What works today — and what remains

Working (verified in CI — 490/490 tests)

  • Offline counter POS: exact-decimal pricing, US/CA tax & PaintCare/eco-fee presets, tills & Z-reports, DB-backed holds (pos_holds), quotes, layaways, returns with provider card refunds, card auto-void on split-tender decline or failed commit, real signed-in cashier attribution, and ESC/POS + ZPL receipt/label bytes
  • Formula tracking: formula lookup by color name/code, customer color history, colorant catalog, and portal formula reorders (tracks formulas only — never drives a tint machine)
  • Contractor AR & back-office: charge accounts, credit limits/holds, FIFO payment allocation, finance charges, Typst PDF statements, purchasing & replenishment, inter-store transfers, physical counts, bulk matrix pricing with margin floors, and QuickBooks IIF / CSV accounting exports
  • Vendor EDI, CRM & delivery: X12 850/855/856/810/832 with 3-way match, CRM activities/tickler/appointments/saved views/lapsed-contractor report, and POD-gated delivery dispatch
  • BI, Scheduling+ & web apps: sales/margin/turns KPIs, PaintCare/eco remittance CSV, shifts/timeclock/labor forecasting, Mobile PWA, authenticated Contractor Portal, and public BOPIS storefront
  • Security, PostgreSQL HQ & Admin UI: Argon2id auth, per-route RBAC, first-run GUI setup, live-tested PostgreSQL HQ ingest, dfs_ store service tokens, F8 dead-letter queue + HQ conflict triage, F10 CORS/rate-limiting/body limits, Admin & Sync UI in pos-desktop, and native Tauri loopback parity

Remaining / pilot integrations

  • Server runtime stubs: df-server worker (DB-persisted job_runs cron scheduler) and df-server standalone remain stubs; docker-compose.yml and the Helm chart still reference the standalone df-api service
  • Live external integrations: Stripe Terminal live calls, real SMTP email delivery (currently file outbox), real SSH SFTP / signed AS2 EDI transport, POD photo blob storage, and native USB/serial printer/drawer wiring in Tauri
  • Auth & catalog polish: audit actor / override reason_code persistence on voids/returns, expired-session janitor, bare badge-tap ID column, product UPC/category columns, mobile PWA offline replay idempotency, and native PostgreSQL column types (currently TEXT parity with SQLite)
  • Mobile & deferred scope: Tauri Mobile (Android/iOS) wrapper is unverified in CI; Benjamin Moore COLORx tint-machine integration is deferred post-v1.0 by design
